# Агент, месячный прогон и автоматизация

Страница `/forecast` содержит разовый прогноз, месячный прогон и настройки
автоматизации. Открытие страницы, просмотр истории и скачивание результатов
не вызывают LLM. OpenAI Responses API получает ключ из `.env`/окружения;
модель по умолчанию — `gpt-4.1-mini`. `.env` не копируется в Docker-образ.

## Инструменты и модели

| Инструмент | Назначение |
|---|---|
| `inspect_data` | Наличие измерений, качество загрузки и явные настройки времени |
| `prepare_features` | Готовность погодного артефакта либо полные прошлые часы телеметрии с возрастом не более 2 ч |
| `fetch_weather` | Допустимый погодный выпуск; при временном отказе одна попытка более раннего выпуска |
| `predict_power` | Погодная модель либо модель по прошлой телеметрии; явный persistence fallback только на телеметрическом маршруте |
| `check_forecast` | Времена, число точек, конечность чисел, диапазон мощности 0–1 |
| `analyze_forecast` | Минимум, максимум, среднее, почасовые изменения, плоский прогноз и резкие перепады; это диагностика, не точность |
| `save_forecast` | Повторная проверка, сохранение чисел, модели, происхождения данных и анализа |

`forecast_mode=auto` сначала проверяет пригодность погодной модели. Ей не нужна
новая SCADA после обучающего периода, но необходим подходящий исторический
прогноз погоды. Если погодного артефакта нет, рассматривается модель по прошлой
телеметрии. Ей и persistence нужны свежие измерения. `forecast_mode=weather`
запрещает подмену погодного прогноза baseline; `telemetry` выбирает маршрут
по измерениям. Непригодная погода на уже выбранном погодном маршруте останавливает расчёт.

Готовность учитывает CSV, timezone, семантику времени, результаты отбора и
`usable_from <= issue_at`. Наличие модели не доказывает доступность нужного
выпуска погоды — он проверяется отдельно. Каталог: `GET /api/ml/models`.
Погодная модель использует допустимый прогноз погоды и календарь;
телеметрическая — прошлые измерения и календарь. Будущие фактические измерения
ветра и мощности не используются. Для погодной модели `evaluation_training_end`
относится к отдельным весам оценки, а `training_end` — к текущим финальным весам.
Нельзя приписывать финальным весам независимую оценку на периоде их дообучения.

Обучение выполняется отдельной явной CLI-командой; оно не является инструментом
LLM и не запускается импортом CSV, открытием страницы или событием автоматизации.
`wind.case` последовательно готовит архив, обучает модели и запускает replay.
Его `execution_mode` относится к оркестрации прогнозов после обучения.

Турбина и время фиксируются сервером; произвольных shell, SQL и файловых
операций у модели нет. LLM ограничена десятью запросами OpenAI и 700 выходными
токенами на запрос; автоматических повторов OpenAI нет. Числа рассчитывают
Python-инструменты. `summary` строится из проверенных результатов;
`llm_summary` сохраняется отдельно как непроверенное свободное пояснение.

## Разовый прогноз

Выберите турбины, настройки времени каждой из них, первую и последнюю отметки
прогноза UTC включительно: от 24 до 48 почасовых значений. Момент расчёта
`issue_at` равен первой отметке минус час и не может быть будущим.
Timezone не заполняется автоматически. Постоянное UTC+6 (`Etc/GMT-6`) остаётся
эмпирической гипотезой; `Asia/Almaty` учитывает исторический перевод часов.

«Проверить данные бесплатно» — локальный preflight без LLM. Для погодного
маршрута он проверяет модель; полнота и доступность погоды проверяются позднее.
«Получить прогноз» повторяет preflight каждой турбины, затем последовательно
запускает настоящую LLM для готовых входов. Остановка очереди не отменяет
уже начатый запрос.

API: `GET /api/agent/status`, `POST /api/agent/preflight`,
`POST /api/agent/runs`, `GET /api/agent/runs?turbine_id=1`,
`GET /api/forecasts/{id}`. Файлы: `DATA_DIR/agent-runs` и `DATA_DIR/forecasts`.

## Февральский месячный прогон

По умолчанию: выпуски ежедневно в **12:00 UTC с 31 января по 28 февраля 2026
включительно**, горизонт 48 часов. Это 29 выпусков на турбину. Новые измерения
SCADA за февраль не подмешиваются. Нужна готовая погодная модель; её отсутствие
блокирует создание задачи. Недопустимая/отсутствующая погода становится ошибкой
выпуска, а не успешным baseline.

Время CSV задаётся явно и применяется ко всем выбранным турбинам. Для разных
настроек нужны отдельные прогоны. Допускаются 1–366 дней, до 32 турбин,
небудущие выпуски. Платный прогон ограничен 128 комбинациями «турбина × выпуск».

- `execution_mode=tools` — по умолчанию: заданная последовательность инструментов
  без LLM и OpenAI-кредитов. Это детерминированный прогон, не решения LLM.
- `execution_mode=llm` — настоящий агент для каждого выпуска, расходует кредиты.
  Требует явного выбора режима и нажатия запуска.

Это поддерживаемые режимы запуска. Отчёт успешного `tools`-прогона не является
подтверждением полного месячного LLM-прогона: для последнего необходим отдельный
отчёт с `execution_mode=llm`, результатами выпусков и журналом инструментария.

Сервер возвращает задачу сразу; интерфейс показывает прогресс, ошибки и выгрузки.
Закрытие страницы не отменяет принятую задачу. Перезапуск процесса не вызывает
скрытый повтор потенциально платного запроса: незавершённые задачи отмечаются
прерванными, сохранённые результаты доступны. Продолжение — CLI `--resume`.
При изменении CSV или координат оставшиеся расчёты отклоняются.

| API | Результат |
|---|---|
| `POST /api/replays` | Создание задачи по расписанию и настройкам |
| `GET /api/replays` | Последние задачи в `items` |
| `GET /api/replays/{id}` | Статус, `progress`, результаты и ошибки |
| `GET /api/replays/{id}/export?kind=forecasts` | CSV всех успешных выпусков |
| `GET /api/replays/{id}/export?kind=coverage` | CSV итогового часового покрытия |
| `GET /api/replays/{id}/export?kind=plant` | Почасовая сумма выбранных турбин в кВт/кВт·ч; нужны подтверждённые номиналы |
| `GET /api/replays/{id}/export?kind=report` | JSON отчёта и происхождения |

Хранилище: `DATA_DIR/replays/<id>/job.json`. Статусы: `queued`, `running`,
`completed`, `partial`, `failed`. `progress.completed` включает успехи и ошибки;
успехи считаются отдельно в `succeeded`. Ошибки не заменяются фиктивными числами.

Для расписания 31 января — 28 февраля покрытие относится к **1–28 февраля UTC**.
Для каждой турбины и целевого часа выбирается последний успешный выпуск строго
раньше целевого часа. Все отдельные горизонты, включая часы за концом месяца,
сохраняются в CSV выпусков. В покрытии пропуски остаются пустыми. Полнота
покрытия не означает известную точность: фактической мощности февраля нет.
При единственном дне выпуска покрытие относится к следующим календарным
суткам UTC; оно может быть неполным в зависимости от часа выпуска и горизонта.

Если до создания задачи пользователь подтвердил номинальную мощность через
карточку OpenStreetMap, снимок входов фиксирует номинал и ссылку на источник.
`power_kw = power × rated_power_kw`, `energy_kwh = power_kw × 1 час`.
Экспорт `plant` суммирует выбранные турбины по целевому часу и требует
подтверждённых номиналов всех турбин; иначе API возвращает 422.
Применение характеристик после создания задачи не меняет старые выгрузки.
Это физический пересчёт прогнозной мощности, а не измеренная энергия.

## Автоматизация по обновлениям

Начальные настройки — `enabled=false`, `execution_mode=tools`. Выберите
турбины, время CSV, горизонт и режим; изменения применяются после сохранения.
Включение с `execution_mode=llm` явно разрешает последующие платные вызовы.
Интерфейс показывает расход до сохранения; импорт сам не включает автоматизацию.

Импорт измерений ставит `data_updated` для подписанной турбины. Обновление NOAA GFS
через `POST /api/weather/gfs` с `turbine_id`, `issue_at`, `horizon` ставит
`weather_updated` именно на переданный `issue_at`. В интерфейсе этому соответствует
«Обновить погоду и пересчитать» с явным выбором момента UTC. При выключенной
автоматизации эта кнопка только загружает погоду. Старый `POST /api/weather`
(Open-Meteo) и произвольные загрузки реестра не запускают пересчёт NWP:
их данные не являются признаками обученной погодной модели.

Импорт/загрузка не ждут агента. Одинаковые тип события, турбина, SHA/ревизия,
настройки и запрошенный момент повторно в очередь не ставятся. Журнал во вкладке
«Автоматизация» показывает результат каждого события и сохранённый прогноз.
При новом SHA CSV прежний артефакт может стать несовместимым; автоматизация
не дообучает его. Требуется явное обучение либо допустимый телеметрический
fallback с отражением выбранного маршрута в отчёте.

После импорта пересчитывается момент последнего сохранённого прогноза турбины.
Если истории нет, выбирается доступность последнего полного часа измерений,
не позднее текущего UTC. Старые измерения не переносятся автоматически на сегодняшнюю дату.
События обрабатываются последовательно. Изменение/выключение настроек отменяет
ещё ожидающие события; уже начатый запрос не отменяется. После сбоя процесса
потенциально платный запрос автоматически не повторяется.

API: `GET/PUT /api/automation`, `GET /api/automation/events`.
Файлы: `DATA_DIR/automation/settings.json`, `DATA_DIR/automation/events/*.json`.

## Историческая проверка оркестрации

23.09.2026 выполнены шесть изолированных сценариев с реальной OpenAI LLM:
healthy, missing_hours, weather_outage, stale_telemetry, time_unconfirmed,
data_updated. В обычном сценарии загружен настоящий архив Open-Meteo; остальные
погодные ответы/отказы моделировались. Будущая мощность 0,99 в прогноз не попала.
Все шесть проверок прошли: 25 390 входных и 677 выходных токенов. Это проверка
прежнего persistence-маршрута, не точности новой модели или покрытия февраля.

Отчёты — `data/agent-validation/<id>/` вне Git. Команда
`uv run python -m wind.simulate` повторяет живые запросы и расходует кредиты.
Проверки ML описаны отдельно в `docs/ml/`.

## Ограничения

Мощность нормализована. Для кВт/кВт·ч и суммарной энергии нужны номинальные
мощности турбин. Время исходной SCADA остаётся явно выбранным допущением.
Профиль всей загрузки `inspect_data` не является срезом признаков на `issue_at`.
Сервер рассчитан на localhost: авторизации и изоляции пользователей нет.
Исторический месячный прогон и реакция на обновления не заменяют постоянный
календарный сервис будущих ежедневных выпусков.
