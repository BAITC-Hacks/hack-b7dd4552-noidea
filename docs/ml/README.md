# ML baseline: прогноз нормализованной мощности

Модуль находится в `src/wind_ml/`, зависимости и lock-файл — в корневых
`pyproject.toml` и `uv.lock`. Команды ниже выполняются из корня репозитория.
Здесь описаны отдельные CLI-инструменты baseline и погодного кандидата.
Подключённая к приложению модель по прошлой телеметрии обучается через
`python -m wind.ml train`: инструкция — в [основном README](../../README.md),
актуальные метрики и ограничения — в [аудите данных](data-audit.md).
Этот документ также сохраняет результаты прежнего baseline-этапа.
Новый подключённый NOAA GFS-маршрут и его проверка описаны отдельно в
[аудите погодной модели](nwp-audit.md); полный сценарий запуска — в основном README.

## Что реализовано

- Строгий адаптер исходных 10-минутных CSV в предварительный почасовой
  контракт. Численные средние появляются только при шести валидных и уникальных
  точках часа; разрывы остаются `partial`/`missing` с null-значениями.
- Persistence baseline: последняя мощность, которая уже стала известна на
  момент выпуска, повторяется на весь горизонт 1–48 часов.
- Объяснимая медианная бинированная кривая «фактическая скорость ветра →
  нормализованная мощность» для каждой турбины. Это диагностическая модель;
  её нельзя оценивать как честный прогноз, если в качестве входа подан будущий
  SCADA-ветер.
- Кандидат `HistGradientBoostingRegressor`: архивный прогноз температуры и
  ветра, горизонт, календарные признаки, последнее доступное измерение и его
  возраст. Направление ветра представлено парой `sin/cos`.
- Последовательная walk-forward проверка. Для fold `[S, E)` fit получает только
  строки с `target_time < S` и `target_available_at <= S`. В оценке остаются
  цели внутри `[S, E)`, доступные к `E`. Пересекающиеся и повторные folds запрещены.
- MAE/RMSE отдельно для `1–24h` и `25–48h`, с числом оценённых часов и долей
  исключений. В audit у строки есть причина: `missing_target`, `missing_lag`,
  `stale_telemetry`, `target_outside_fold`, `weather_unverified` или `weather_not_available`.
- Сохранение `model.joblib` и `manifest.json`: тип модели, ID турбины, границы
  обучения, временная конфигурация, схема признаков, контракт погоды и метрики.

## Контракт с первым этапом

Почасовой CSV (`time` пока wall-clock, без неявного UTC):

```text
time,wind_speed,power,temperature,sample_count,valid_count,completeness,quality
```

`quality` принимает `complete`, `partial`, `missing`. У полного часа ровно
шесть валидных точек и `completeness=1`; для остальных трёх численных средних
должны быть null. Модуль не заполняет пропуски.

Для новых импортов вызывайте `hourly_from_scada_csv(path, config=time_config)`.
Адаптер сначала локализует исходные 10-минутные отметки и переводит их в UTC;
при `interval_end` вычитает 10 минут и только затем усредняет час. Он добавляет
`time_utc` (начало часового интервала), `available_at` (конец часа),
`source_timezone` и `source_timestamp_semantics`. Эти колонки сохраняются в CSV.
Смена конфигурации после агрегации запрещена. Старый hourly без этих колонок
допускается только с `interval_start`: восстановить корректный `interval_end`
из среднего `:00..:50` невозможно, нужен повторный импорт raw.

Консолидированный архив погоды использует только UTC-время:

```text
time,run,available_at,historical_eligibility,
temperature_2m,wind_speed_10m,wind_speed_100m,wind_direction_100m
```

`run` — инициализация численной модели, **не** публикация. Для обучения и
оценки бустинга или честной weather-driven кривой нужны одновременно
`historical_eligibility=verified` и известный `available_at`; для признаков
используется лишь строка с `available_at <= issue_time`. Нормализатор одного
ответа Open-Meteo не угадывает `available_at`: без подтверждения он выдаёт
`unverified`, и такая строка будет исключена.

## Время и границы знания

CLI требует два явных параметра:

```text
--measurement-timezone Etc/GMT-6
--timestamp-semantics interval_start
```

Постоянный UTC+6 поддерживается сопоставлением с погодой, но пока не подтверждён
настройками SCADA. `Asia/Almaty` и `Etc/GMT-6` — разные гипотезы после марта 2024.
Часовой интервал `[10:00, 11:00)` становится доступен в `11:00` независимо от
семантики исходных 10-минутных меток. Для `interval_end` этот час состоит из
исходных меток `10:10..11:00`. Неоднозначное время при импорте raw вызывает
ошибку; legacy hourly исключает такой час. После изменения временной гипотезы
данные нужно заново агрегировать и модель переобучить. Доставка без задержки
остаётся явным допущением. Лаг старше двух часов блокирует прогноз.

Погодный пример `/tmp/hackalem-weather-sample.json` прочитан: это 72 непрерывные
UTC/GMT часа `2026-01-31T00:00`–`2026-02-02T23:00` с запрошенными четырьмя
переменными. Он не содержит подтверждённого времени публикации и поэтому не
может использоваться для честной ретроспективной оценки.

## Команды

Установить зависимости из зафиксированного lock-файла:

```bash
uv sync --frozen --group dev
```

Преобразовать два исходных файла. Команда ничего не интерполирует:

```bash
uv run python -m wind_ml prepare-hourly \
  --input '/home/qialsyz/Загрузки/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv' \
  --measurement-timezone Etc/GMT-6 --timestamp-semantics interval_start \
  --output /tmp/turbine-1-hourly.csv
```

Нормализовать уже сохранённый ответ Single Runs. Не указывайте `available_at`,
пока оно не доказано: полученный CSV будет только для проверки схемы.

```bash
uv run python -m wind_ml normalize-weather \
  --input /tmp/hackalem-weather-sample.json \
  --output /tmp/weather-unverified.csv \
  --run 2026-01-31T00:00:00Z
```

Проверить один 72-часовой API-запрос до массовой загрузки. Команда записывает
ответ и рядом метаданные с SHA-256, но намеренно ставит
`historical_eligibility=unverified` и `available_at=null`.

```bash
uv run python -m wind_ml weather-check \
  --latitude 43.645150 --longitude 78.535604 \
  --run 2026-01-31T00:00:00 --output /tmp/weather-check.json
```

Оценить persistence без погоды; границы fold — UTC и правая граница
исключается:

```bash
uv run python -m wind_ml validate \
  --model persistence --measurements /tmp/turbine-1-hourly.csv --turbine-id 1 \
  --measurement-timezone Etc/GMT-6 --timestamp-semantics interval_start \
  --fold 2025-11-01T00:00:00Z/2025-12-01T00:00:00Z \
  --audit-output /tmp/persistence-audit.csv
```

После получения **verified** архива погоды сначала оценивают бустинг, а потом
отдельной командой обучают финальный артефакт. Не интерпретируйте второй шаг как
оценку качества:

```bash
uv run python -m wind_ml validate \
  --model boosting --measurements /tmp/turbine-1-hourly.csv \
  --weather /local/verified-weather.csv --turbine-id 1 \
  --measurement-timezone Etc/GMT-6 --timestamp-semantics interval_start \
  --fold 2025-10-01T00:00:00Z/2025-11-01T00:00:00Z

uv run python -m wind_ml train \
  --model boosting --measurements /tmp/turbine-1-hourly.csv \
  --weather /local/verified-weather.csv --turbine-id 1 \
  --measurement-timezone Etc/GMT-6 --timestamp-semantics interval_start \
  --train-end 2026-02-01T00:00:00Z \
  --artifacts-dir /local/ml-artifacts/turbine-1
```

`train` требует явный `--train-end`. Инференс проверяет, что `issue_at` не раньше
границы обучения, ID и временная конфигурация совпадают с артефактом, а горизонт
не превышает `trained_horizon_hours`. Старые артефакты без горизонта нужно
переобучить. Инференс для 48 часов использует состояние измерений только на `issue_at`:

```bash
uv run python -m wind_ml infer \
  --artifacts-dir /local/ml-artifacts/turbine-1 \
  --measurements /tmp/turbine-1-hourly.csv --weather /local/verified-weather.csv \
  --issue-at 2026-02-01T00:00:00Z --horizon 48 --output /tmp/forecast.csv
```

## Исторические проверки до аудита утечек

`ruff check src/wind_ml tests/ml` прошёл без замечаний; `pytest -q tests/ml`
прошёл: **9 passed**. Fixtures отдельно проверяют пропуски без интерполяции,
отсутствие будущего SCADA lag, ограничение `available_at <= issue_time`, запрет
`unverified` погоды, изменение смещения Asia/Almaty, границу замороженного fit
и manifest.

Адаптер был запущен на предоставленных CSV (локальные результаты в `/tmp`):

| Турбина | complete | partial | missing |
| --- | ---: | ---: | ---: |
| 1 | 23 667 | 96 | 1 629 |
| 2 | 24 785 | 219 | 388 |

Следующие числа сохранены для происхождения прежнего результата, а не как
метрики исправленной модели. Они рассчитаны с `Asia/Almaty`, без фильтра старых
лагов и без обрезки целей по концу fold. Их требуется пересчитать с новым контрактом.

Persistence оценён без погоды на двух UTC-folds
`2025-10-01..2025-11-01` и `2025-12-01..2026-01-01` (всего 71 424 запроса на
турбину). Это baseline, а не результат финального теста:

| Турбина | Горизонт | MAE | RMSE | оценено | исключено |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | 1–24 ч | 0.29825 | 0.41920 | 34 248 | 1 464 (4.10%) |
| 1 | 25–48 ч | 0.36117 | 0.47765 | 34 248 | 1 464 (4.10%) |
| 2 | 1–24 ч | 0.29901 | 0.42151 | 34 104 | 1 608 (4.50%) |
| 2 | 25–48 ч | 0.36059 | 0.47848 | 34 104 | 1 608 (4.50%) |

Один проверочный запрос Open-Meteo Single Runs для запуска
`2026-01-30T00:00` вернул 72 UTC/GMT часа `2026-01-30T00:00`–
`2026-02-01T23:00`, все четыре запрошенные переменные и SHA-256
`df28642204004b4137b0eb37f8c1346686fdd9d0257fc8e280fd2df9ee4c1d28`.
Доступность ответа сейчас не доказывает его историческую публикацию, поэтому
metadata остаётся `available_at=null`, `historical_eligibility=unverified`.

## Ограничения прежних артефактов и погодного кандидата

Аудит существующих `/tmp/hackalem-artifacts` обнаружил только артефакты
persistence и power curve для турбины 1, с конфигурацией `Asia/Almaty` и границей
обучения `2026-02-01`. Январь уже был использован в финальном обучении power curve,
поэтому его нельзя называть нетронутым тестом. Отдельного реального артефакта
погодного бустинга и его метрик в проверенных тогда каталогах не было. Старые CSV аудита допускают
лаг до 52 часов (1 175 и 1 263 оценённых строки с лагом больше двух часов).

В основной копии исправлены прежняя утечка при `interval_end`, отсечение fit
по времени доступности цели, проверка артефакта на инференсе и пересечение целей
validation folds. Случайный внутренний split `HistGradientBoostingRegressor`
отключён (`early_stopping=False`): настройка числа итераций должна использовать
отдельную временную валидацию. Внешний walk-forward ранее не использовался этим
внутренним split; проблема относилась к отбору итераций внутри обучающего периода.

В переданных измерениях нет фактической мощности февраля 2026, поэтому этот
репозиторий не заявляет MAE/RMSE финального теста. На момент прежнего baseline-аудита
полный архив исторически доступных прогнозов ещё не был подготовлен, а погодный
кандидат проверялся синтетическими fixtures. Эти ограничения прежнего этапа
не описывают состояние нового NOAA GFS-маршрута: его реальные проверки и границы
оценки приведены в [nwp-audit.md](nwp-audit.md). Артефакты, данные и бинарные модели
в Git не добавляются.
