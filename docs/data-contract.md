# Контракты измерений, погоды и прогнозов

Доступ к данным — через HTTP API или локальные Parquet. ML-модули не зависят
от React или FastAPI. Рабочий каталог задаётся `DATA_DIR`, по умолчанию
`data/workspace/`; старые полные импорты в `data/` сами в него не подмешиваются.

## Измерения

`GET /api/turbines` возвращает `items`: активные турбины с `id`, названием,
координатами и `has_data`. После импорта появляются `hourly_path`, `sha256`,
границы и качество, `dataset_kind` (`full`/`demo`), `timezone="unconfirmed"`.
Пути считаются относительно `DATA_DIR`. Создание — `POST /api/turbines`,
импорт CSV — `POST /api/turbines/{id}/import`, multipart-поле `file`.
Удаление перемещает регистрацию в корзину и сохраняет файлы; восстановление
не требует повторного импорта. В модель не следует включать турбину только
по наличию оставшегося файла: её активность проверяется через каталог.

| Поле почасового Parquet | Тип | Значение |
|---|---|---|
| `time` | datetime без timezone | Начало часового бакета в времени CSV |
| `wind_speed` | float/null | Средняя скорость ветра, м/с; высота датчика неизвестна |
| `power` | float/null | Средняя нормализованная мощность, [0,1] |
| `temperature` | float/null | Средняя температура, °C |
| `sample_count` | int | Количество исходных строк |
| `valid_count` | int | Минимальное число валидных значений трёх метрик |
| `completeness` | float | `valid_count / 6` |
| `quality` | string | `complete`, `partial`, `missing` |

Если `quality != complete`, три численные метрики равны null. Интерполяции нет.
Отсутствующие часы добавляются только между границами исходного ряда.
HTTP сохраняет null и ISO-время без смещения. Это представление для просмотра,
а не автоматическое утверждение об UTC или доступности признаков.

Для признаков и обучающих целей используется исходный `*-10min.parquet`:
локализация выбранным timezone, перевод в UTC, сдвиг на −10 минут для
`interval_end`, затем усреднение полного часа. `interval_start` не требует
этого сдвига. Почасовая цель описывает интервал `[time_utc, time_utc + 1h)`;
значение считается известным в `available_at = time_utc + 1h`.
Задержка доставки телеметрии пока не моделируется. Неоднозначные местные времена
не разрешаются молчаливой догадкой. Legacy-hourly с неясной семантикой конца
интервала нельзя считать эквивалентом пересборки из исходных 10 минут.

Постоянное UTC+6 (`Etc/GMT-6`) поддерживается сопоставлением данных, но остаётся
гипотезой. `Asia/Almaty` учитывает исторический перевод часов и не эквивалентен
постоянному +6. Начало/конец исходного интервала также требуют подтверждения.
Подробности: `docs/timezone-audit.md`.

## Диагностический архив Open-Meteo

`GET /api/weather?turbine_id=1` — сохранённые выпуски;
`GET /api/weather/{id}` — метаданные и `points`.
В точках: `time` с +00:00, `temperature_2m` (°C), `wind_speed_10m` и
`wind_speed_100m` (м/с), `wind_direction_100m` (градусы).
Один выпуск содержит 72 последовательных часа от инициализации, включая час 0.
Это не 72 будущих часа от момента публикации. Отдельные null подсчитываются;
полностью пустая переменная отклоняется.

Сохраняются `run`, `retrieved_at`, `model`, параметры, координаты запроса и сетки,
`raw_path`, SHA-256, единицы и пропуски. У прежних Single Runs:
`available_at=null`, `historical_eligibility="unverified"`.
Инициализация `run` и время загрузки сейчас не доказывают публикацию в прошлом.
Эти записи нельзя автоматически повышать до verified.

## Погода для исторического прогнозирования

Адаптер `wind.archive.fetch_issue_weather` возвращает именно выпуск прогноза
для заданных `turbine_id`, `issue_at` и горизонта 24–48 часов. Используется
NOAA GFS 0.25°, предоставленный архивом Dynamical. Основной кандидат — 00 UTC
дня расчёта, резервный — 00 UTC предыдущего дня. Замена модели или использование
реанализа в качестве fallback не допускаются.

Общий результат содержит `run`, `available_at`, `provider="noaa"`,
`model="noaa_gfs_025"`, `availability_policy="noaa_s3_last_modified"`,
`historical_eligibility="verified"`, `eligible=true`, `sha256`,
`points` и `provenance`. Метки verified/eligible выдаются после проверки,
не на основании пользовательского флага доверия.

Каждая точка: `time`, `run`, `available_at`, `historical_eligibility`,
`temperature_2m`, `wind_speed_10m`, `wind_speed_100m`, `wind_direction_100m`.
Время — UTC, ветер — м/с, температура — °C, направление — градусы.
Нужны все целевые часы `issue_at + 1h ... issue_at + horizon`.

`available_at` — максимум S3 Last-Modified исходных NOAA GRIB-объектов,
покрывающих используемые часы. Каждый такой объект должен быть опубликован
не позднее `issue_at`. `provenance` содержит координаты, ячейку сетки,
версию/снимок архива Dynamical, SHA нормализованных точек и свидетельств
публикации, а также `source_objects` с ключом, URL, временем, ETag и размером.

Это свидетельство публикации оригинальных NOAA GRIB, **не доказательство,
что API Dynamical существовал в исторический момент**. Используется архивная
форма прогнозных значений с документированным преобразованием исходных полей;
округление компонентов ветра необходимо учитывать при воспроизводимости.
Погодная модель проверяет соответствие погодного контракта обучению.

## Запрос и результат прогноза

Разовый запрос `AgentRequest`: `turbine_id`, `issue_at` (целый час UTC,
не будущее), `measurement_timezone`, `timestamp_semantics`, `horizon` 24–48,
`event` (`manual`/`data_updated`/`weather_updated`), `forecast_mode`
(`auto`/`weather`/`telemetry`). Пустые настройки времени блокируют расчёт.

Результат в `DATA_DIR/forecasts/<id>.json`: запрос, имя модели,
`model_metadata`, подготовленные признаки, `points` и `analysis`.
Каждая точка содержит ISO UTC `time` и нормализованную `power` в [0,1].
Метки — начала прогнозируемых часовых интервалов, от `issue_at + 1h`
до `issue_at + horizon`. Это не кВт и не кВт·ч.
При `horizon=48` последний интервал заканчивается в `issue_at+49h`:
контракт задаёт 48 будущих начал часа, а не окно `[issue_at, issue_at+48h)`.
Происхождение погодного выпуска и контрольная сумма модели сохраняются
в метаданных. Анализ диапазона и скачков не является MAE/RMSE.

Каталог `GET /api/ml/models` содержит готовность модели для конкретной
версии CSV и временной конфигурации. `training_end` — граница текущего fit,
`usable_from` — начало допустимого применения; для отдельного frozen fit
оценки служит `evaluation_training_end`. Периоды валидации/контроля и метрики
не следует переносить на новые данные без повторной проверки.

## Месячный прогон и экспорт

`POST /api/replays` принимает `turbine_ids`, время CSV, `start_date`,
`end_date`, `issue_hour_utc`, `horizon`, `execution_mode=tools|llm`.
Поля ответа: `id`, `request`, `status`, `progress`, `errors`, `results`
и после завершения `summary`. SHA CSV и координаты фиксируются при создании;
их изменение не должно незаметно менять входы уже запущенного прогона.

CSV выпусков содержит `turbine_id`, `issue_at`, `target_time`, `power`,
`lead_hours`, `forecast_id`, `model`, `model_sha256`, `weather_run`,
`weather_available_at`, `weather_source`, `weather_sha256`, `units`,
`rated_power_kw`, `power_kw`, `energy_kwh`, `capacity_source_url`.
CSV покрытия выбирает последний успешный выпуск строго до целевого часа,
сохраняя пустую `power` при отсутствии прогноза. Диапазон покрытия — UTC-дни
после `start_date` по `end_date` включительно: расписание 31.01–28.02
покрывает 01.02–28.02. Прогнозы отдельных выпусков могут выходить за этот диапазон.
Для одного дня выпусков диапазон покрытия — следующие сутки UTC.
JSON-отчёт сохраняет режим исполнения и ошибки. `tools` не следует выдавать
за trace решений LLM, а успешное покрытие — за оцененную точность.

Полной мощности февраля в исходных CSV нет. Номинал учитывается только при
`capacity_status=user_confirmed_osm`: пользователь явно сопоставил объект OSM
с турбиной и применил характеристики. `input_snapshots` фиксирует номинал
и источник в момент создания задачи. Без такого подтверждения физические
поля остаются пустыми. При известном номинале `power_kw=power×rated_power_kw`,
а `energy_kwh=power_kw×1 час` для часового интервала.
Формулы предполагают исходную нормировку `P/Pном`. Задание её явно не определяет,
поэтому кВт/кВт·ч условны до подтверждения формулы организаторами. Подтверждение
характеристик OSM устанавливает выбранный номинал, но не способ нормировки CSV.

`export?kind=plant` суммирует выбранные турбины по целевому часу; требуются
подтверждённые при создании задачи номиналы всех турбин, иначе API возвращает 422.
Отсутствующий прогноз не превращается в нулевую генерацию. Выгрузка относится
только к выбранным турбинам, а не автоматически ко всей площадке. Сумма
нормализованных рядов сама по себе не является энергией парка. OSM остаётся
публичным источником характеристик, а не паспортом оборудования.
